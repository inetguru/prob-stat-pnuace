해시와 해시 테이블

확률통계 · Topic 1 보충자료 — 슬라이드 32번 "오늘 배운 게 어디에 쓰이나" 의 Hashing

슬라이드에서 "서로 다른 키가 같은 버킷에 떨어질 확률은 생일 문제와 같은 구조" 라고만 하고 지나갔다. 그 말을 이해하려면 먼저 해시 테이블이 무엇인지 알아야 한다. 자료구조 과목에서 배우겠지만, 여기서는 확률 이야기에 필요한 만큼만 짚는다.

1. 문제 — 100만 개에서 하나 찾기

학번으로 학생을 찾는 프로그램을 만든다고 하자. 데이터가 100만 개 있다. 가장 단순한 방법은 처음부터 하나씩 비교하는 것이다.

순차 탐색 운이 나쁘면 100만 번
찾는 값이 맨 뒤에 있으면 전부 확인해야 한다. 평균 50만 번. 데이터가 늘면 그만큼 느려진다.
해시 테이블 대개 한 번
값을 보고 위치를 계산한다. 데이터가 100만 개든 1억 개든 계산 한 번이면 자리를 안다.

발상이 이렇다. 물건을 아무 데나 넣고 나중에 뒤지는 대신, "이 물건은 몇 번 칸"이라는 규칙을 미리 정해두는 것이다. 넣을 때도 찾을 때도 같은 규칙을 쓰면, 뒤질 필요가 없다.

2. 해시 함수 — 무엇이든 숫자로

그 규칙을 만드는 것이 해시 함수(hash function) 다. 글자든 그림이든 파일이든 넣으면 정해진 범위의 숫자 하나를 뱉는다.

해시 함수  h  :   아무 데이터  ⟶  0 … m−1 중 하나의 숫자

아래에서 쓸 해시 함수는 교육용으로 아주 단순하게 잡았다.

h(단어) = (글자 코드를 전부 더한 값) % 8    ← % 는 나머지 연산

해시 함수가 갖춰야 할 성질은 셋이다.

① 같은 입력 → 같은 출력 언제 계산해도 같아야
그래야 넣을 때와 찾을 때 같은 칸으로 간다.
② 빠를 것 계산이 탐색보다 느리면 의미가 없다
보통 덧셈·곱셈·비트연산 몇 번으로 끝난다.
③ 고르게 흩어질 것 한쪽에 몰리면 안 된다
⭐ 여기서 확률이 등장한다. 뒤에서 다시 본다.

3. 직접 넣어 보기

단어를 넣으면 해시 계산 과정이 단계별로 보이고, 공이 해당 칸으로 들어간다. 같은 칸에 둘 이상 들어가면 주황색으로 표시된다.

h(단어) = 글자 코드 합 % 8
단어를 넣어 볼 것.
⚠️ 실제 해시 함수는 이것보다 훨씬 복잡하다. 위 함수는 글자 순서를 무시한다. 그래서 lemon 과 melon 은 더한 값이 똑같이 539 라 반드시 같은 칸에 떨어진다. 실무에서 쓰는 해시(SHA-256, MurmurHash 등)는 순서까지 반영하고, 입력이 한 글자만 달라도 결과가 완전히 달라지도록 설계돼 있다.

4. 찾을 때 무슨 일이 벌어지나

왼쪽은 처음부터 하나씩 비교하고, 오른쪽은 해시로 자리를 계산해 바로 간다. 같은 값을 찾게 시켜 보고 비교 횟수를 견주어 볼 것.

찾을 값: —

순차 탐색 — 배열

비교 0 번

해시 테이블

비교 0 번

해시 쪽은 계산 한 번으로 칸을 찾고, 그 칸 안에서만 비교한다. 칸에 하나만 들어 있으면 비교도 한 번이다. 데이터가 몇 개든 상관없다 — 이것이 평균 O(1) 이라고 부르는 성질이다.

5. 충돌 — 피할 수 없다

서로 다른 키가 같은 칸으로 가는 일을 충돌(collision) 이라 한다. 위에서 이미 보셨을 것이다. 충돌에는 원인이 두 가지 있다.

원인 1 — 칸이 모자라서 비둘기집 원리
가능한 키는 무한한데 칸은 m 개다. 키가 m 개를 넘으면 충돌은 반드시 일어난다. date(414) 와 fig(310) 는 합이 다른데도 8로 나눈 나머지가 둘 다 6이다.
원인 2 — 함수가 나빠서 설계 결함
lemon 과 melon 은 합 자체가 같다. 좋은 해시 함수라면 이런 일이 없어야 한다. ⭐ 원인 1은 어쩔 수 없고, 원인 2는 고칠 수 있다.

그래서 충돌을 "막지" 않고 "처리"한다

체이닝 한 칸에 여러 개를 매단다
위 시연이 이 방식이다. 칸마다 목록을 두고 쌓는다. 찾을 때는 그 목록만 훑으면 된다.
개방 주소법 옆 칸으로 밀어 넣는다
자리가 찼으면 다음 빈칸을 찾아간다. 메모리를 아끼지만 지우기가 까다롭다.

6. ⭐ 여기서 확률이 필요해진다

"충돌이 가끔 일어난다"와 "충돌이 자주 일어난다"는 전혀 다른 이야기다. 전자면 해시 테이블은 빠르고, 후자면 결국 순차 탐색과 다를 바 없어진다. 그러니 물어야 한다 — 충돌은 얼마나 자주 일어나는가?

키가 칸에 고르게, 서로 독립적으로 떨어진다고 가정하면 (Topic 1 의 등확률 가정이다) 계산할 수 있다. 칸이 m 개, 키가 n 개일 때 충돌이 하나도 없을 확률은 이렇다.

ℙ[충돌 없음] = m/m × (m−1)/m × (m−2)/m × ⋯ × (m−n+1)/m

ℙ[충돌 있음] = 1 − ℙ[충돌 없음]    ← 여사건이다

이 식이 낯익다면 맞다. m = 365, n = 23 을 넣으면 0.5073 이 나온다. 생일 문제 그 값이다. 해시 충돌과 생일 문제는 완전히 같은 문제다 — 칸이 날짜냐 버킷이냐만 다르다.

충돌은 생각보다 훨씬 빨리 온다. 칸이 100만 개나 되는데 키가 1,178개만 들어와도 충돌 확률이 절반을 넘는다. 전체의 0.1% 밖에 안 찼는데 말이다. 그래서 해시 테이블 설계는 "충돌을 없애기"가 아니라 "충돌을 싸게 처리하기" 가 목표다.

⭐ 이 계산을 직접 해 보는 것이 과제 1(생일 문제) 이다. 거기서 만든 코드의 365 를 버킷 수로 바꾸면 그대로 해시 충돌 계산기가 된다.

7. 어디에 쓰이나

언어 기본 자료형 Python dict · set
d["key"] 가 빠른 이유가 해시다. Java HashMap, C++ unordered_map 도 같다.
데이터베이스 해시 인덱스 · 조인
수억 행에서 조건에 맞는 행을 찾을 때, 또 두 표를 이어 붙일 때 쓴다.
캐시 중복 계산 피하기
입력을 해시로 만들어 "전에 계산한 적 있나"를 즉시 확인한다. 웹 캐시, 메모이제이션.
무결성 검사 파일이 바뀌었나
내려받은 파일의 해시를 원본과 비교한다. 한 비트만 달라도 값이 완전히 달라진다.
비밀번호 저장 원문을 저장하지 않는다
해시만 저장해 두고 로그인할 때 비교한다. ⚠️ 이때는 일부러 느린 해시를 쓴다.
Git · 블록체인 내용으로 이름 짓기
Git 의 커밋 ID 가 내용의 해시다. 블록체인도 같은 원리로 위변조를 막는다.
같은 "해시"인데 목적이 정반대인 경우가 있다. 해시 테이블용 해시는 빠를수록 좋지만, 비밀번호용 해시는 느릴수록 좋다. 공격자가 무작위로 대입할 때 한 번 시도에 오래 걸리게 만들어야 하기 때문이다. 이름은 같아도 설계 목표가 다르다.
